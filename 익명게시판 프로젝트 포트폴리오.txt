2. 발표 내용 요약 

2_1) 프로젝트 주제 : 익명 게시판 만들기

2_2) 설계 시 주안점 : 
	게시글의 작성자가 누구인지 모를 때 어떻게 작성자인지 확인하고 게시글을 생성, 수정, 삭제를 할 수 있는지를 중점으로 만들었습니다.

2_3) 테이블 구성 설명 : 
	1) 테이블 명 :	ANNO_BOARD (게시글 테이블)
	
	    컬럼 명 :		BOARD_NO (게시글 번호)
					NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
				BOARD_TITLE (게시글 제목)
					NVARCHAR2(200) NOT NULL
				BOARD_CONTENT (게시글 내용)
					NVARCHAR2(2000) NOT NULL
				BOARD_COUNT (조회수)
					NUMBER DEFAULT 0 NOT NULL
				USER_ID (게시글 작성자 아이디)
					VARCHAR2(30) NOT NULL
				USER_PWD (게시글 작성자 비밀번호)
					VARCHAR2(100) NOT NULL
				CATEGORY_NO (카테고리 번호)
					NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
				DEL_YN (삭제 여부)
					CHAR(1) DEFAULT 'N' CHECK(DEL_YN IN('Y', 'N')) NOT NULL
				REG_DATE (작성 날짜)
					TIMESTAMP DEFAULT SYSTIMESTAMP NOT NULL
						
	    설명 :		게시글 작성시 아이디와 비밀번호 값을 받아서 익명이지만 해당 게시글을 수정 및 삭제할 권한이 있는지 확인했습니다.
				카테고리 테이블을 따로 만들어서 현재 서비스 중인 카테고리만 이용 할 수 있게 했습니다.
				삭제 여부를 확인 해서 비활성시 일반 사용자에게는 안보이는 용도로 만들었습니다.

	2) 테이블 명 :	ANNO_CATEGORY (게시글 카테고리 테이블)
	
	    컬럼 명 :		CATEGORY_NO (카테고리 번호)
					NUMBER GENERATED ALWAYS AS IDENTITY PRIMARY KEY
				CATEGORY_NAME (카테고리 이름)
					NVARCHAR2(20) NOT NULL 
		
	    설명 :		게시글의 카테고리를 따로 분리 해서 게시글 작성시 없는 카테고리로 만드는 걸 방지하고 카테고리를 추가, 수정, 삭제가 필요할 때 유지보수하기 쉽게 따로 뺐습니다.

	3) 테이블 명 :	ANNO_ADMIN (관리자 테이블)
	
	    컬럼 명 :		ADMIN_ID (관리자 아이디)
					VARCHAR(45) PRIMARY KEY
				ADMIN_PWD (관리자 비밀번호)
					VARCHAR(100) NOT NULL
				ROLE (관리자 권한 등급)
					VARCHAR2(20) NOT NULL
				CREATE_DATE (생성 날짜)
					DATE DEFAULT SYSDATE
				DEL_YN (삭제 여부)
					CHAR(1) DEFAULT 'N' CHECK(DEL_YN IN ('Y' , 'N'))
						
	    설명 :		익명 게시판을 관리 하는 사람인지 확인 하기 위해 만들었습니다.
				현재는 관리자 등급이 하나지만 Spring Security를 이용하기 위해 따로 관리자 권한 등급 컬럼이 있습니다.

	4) 테이블 명 :	ANNO_TOKEN (관리자 토큰용 테이블)

	    컬럼 명 :		admin_ID (관리자 아이디)
					VARCHAR2(20) NOT NULL REFERENCES ANNO_ADMIN ON DELETE CASCADE
				TOKEN (토큰)
					VARCHAR2(300) NOT NULL
				EXPIRATION (만료일)
					NUMBER NOT NULL
	
	    설명 :		관리자로 로그인시 토큰 관리를 위한 테이블입니다.

	

2_4) 구현하면서 겪었던 문제점 및 해결방법
	1) 문제 :	익명으로 하기 때문에 누가 게시글을 만들었는지 모르기 때문에 수정 및 삭제 할 때 해당 게시글을 만든 사람인지 구별할 수 없는 문제
	    해결법 :	게시글 작성시 사용자가 해당 게시글용 아이디와 비번을 입력하게 해서 수정 및 삭제할 때 아이디와 비번을 확인하여 작성자를 구별했습니다.

	2) 문제 :	익명 게시판 특성상 누가 게시글에 작성자가 익명으로 표시하기 때문에	모든 게시글의 작성자가 익명으로 통일 되어서 밋밋해지는 문제
	    해결법 :	해당 게시글의 작성된 날짜의 밀리초 기준으로 10가지 형용사와 10가지 동물 이름으로 조합된 이름을 만들어서 익명성은 유지하되 게시판을 밋밋하지 않게 했습니다.
	개선할 점 :	서비스 단에서 게시글 목록 조회나 상세 게시글 조회 할 때마다 해당 게시판의 작성날짜를 확인해서 만든 다음에 보이게 했는데 게시글 테이블에 동물 이름 컬럼을 따로 만들어서 게시글 작성시 동물이름을 만들어 넣어야 합니다.

	3) 문제 :	테이블에 작성 날짜를 TIMESTAMP로 받아서 게시글에 날짜 표시가 0.001밀리초까지 표시 되는 문제
	    해결법 :	서비스 단에서 해당 날짜가 오늘인지, 어제인지, 올해인지를 확인하여 오늘이면 "시:분" | 어제이면 "어제 시:분" | 올해이면 "월.일 시:분" | 그 외엔 "년.월.일 시:분 으로 표시 되게 했습니다.
	개선할 점 : 해당 작업을 DB단에서 할 수 있게 해야됩니다.

	4) 문제 :	효율적인 작업을 위해 DB테이블을 무엇을 할 지 정하고나서 앞단(React), 뒷단(Spring Boot)으로 나눠서 작업을 했는데 합치고 나니 오류가 나는 문제
	    해결법 :	앞단, 뒷단에서 각각 무엇을 요청하고 보내는지 확인해서 이름이나 자료형들을 수정해서 작업했습니다.
	개선할 점 :	분업을 하기전에 DB테이블만 정하지 말고 무엇을 요청하고 받을지도 제대로 정하고 작업해야됩니다.

	5) 문제 :	각자 작업한 결과물을 깃허브에 올리면서 작업을 했는데 어떻게 해야 충돌이 안나고 서로 공유할 수있는 방법을 모르는 문제
	    해결법 :	일단 각자의 브런치를 만들어서 작업물을 올려서 충돌나지 않게 한 후에 다른 사람이 올린 브런치를 따로 받은 다음에 작업물을 합쳤습니다.
	개선할 점 : 따로 받아서 일일히 수작업으로 합치는 방법이 아닌 더 나은 방법 알아오기

	6) 문제 :	집에서 작업하기 위해 깃허브에서 클론으로 받아서 작업하려는데 개발 설정(DB 위치, 아이디, 비번 등)이 달라서 작동을 안하는 문제
	    해결법 :	집에서의 개발 환경으로 맞춰서 하면 매번 받을 때마다 설정을 바꿔야 하기 때문에 집과 학원에서의 설정을 최대한 똑같이 만들었습니다.
